## D-001. 블루투스로 폰 화면을 볼 수 있을까? (2026-11-24)
- **고민:** 폰과 노트북이 이미 블루투스로 연결되어 있으니, 그걸로 폰 화면을 노트북에서 보고 싶다.
- **선택지:**
  - 블루투스 Classic: 실제 속도 1~2Mbps. H.264로 압축해도 480p, 10~15fps 정도가 한계입니다.
  - 블루투스 LE: 수백 kbps. 사실상 슬라이드쇼입니다.
  - Wi-Fi / USB: 수십~수백 Mbps. 1080p 60fps가 가능합니다.
- **결정:** 화면 전송은 Wi-Fi로 합니다. 블루투스는 쓰지 않습니다.
- **이유:** 블루투스는 대역폭이 너무 작습니다. 폰은 안드로이드이고, 보기뿐 아니라 조작까지 원했습니다.
- **남은 걱정:** 블루투스를 "폰이 가까이 있으면 자동 연결" 신호로 쓰는 아이디어는 나중 과제입니다.

## D-002. 직접 만들까, scrcpy를 쓸까? (2026-11-24)
- **고민:** 화면 보기와 조작을 처음부터 직접 만드는 건 큰 작업입니다.
- **결정:** 우선 scrcpy(무료 오픈소스)를 써서 바로 쓸 수 있게 했습니다.
- **이유:** scrcpy는 화면 보기와 조작을 지연 거의 없이 이미 해줍니다.

## D-003. USB 케이블이 없다 (2026-11-25)
- **고민:** 보통 처음 한 번은 USB로 연결해야 하는데 케이블이 없습니다.
- **결정:** 안드로이드 11 이상의 **무선 디버깅 + 페어링 코드**로 처음부터 Wi-Fi로만 연결합니다.

## D-004. Wi-Fi가 바뀌면 연결이 안 된다 (2026-11-25)
- **고민:** 처음 페어링한 Wi-Fi(5G_36)와 지금 Wi-Fi(5G_39)가 달랐습니다. 그래서 IP(.21 → .7)와 포트가 모두 바뀌어 연결되지 않았습니다.
- **결정:** 같은 Wi-Fi에서 폰이 알리는 주소를 자동으로 찾게 했습니다(mDNS). 못 찾을 때만 직접 입력합니다.
- **이유:** 무선 디버깅은 켤 때마다 포트가 바뀌어서, 매번 입력하는 건 불편합니다.
- **남은 걱정:**
  - 다른 Wi-Fi에서도 **같은 Wi-Fi에만 있으면** 연결됩니다. 다만 Wi-Fi가 바뀌면 폰이 무선 디버깅을 끄므로 다시 켜야 합니다.
  - 카페, 호텔, 게스트 Wi-Fi는 기기끼리 통신을 막아서 안 됩니다. 이럴 때는 폰 핫스팟을 쓰면 됩니다.

## D-005. scrcpy에 어떤 기능을 더할까? (2026-11-25)
- **고민:** 키보드, Wi-Fi에서의 화질과 끊김, 폰 화면과 별개인 화면에서 앱 실행
- **결정:**
  - 키보드: `--keyboard=uhid`. 폰이 노트북 키보드를 실제 키보드로 인식해서 한글도 됩니다.
  - 화질: 하드웨어 H.265가 있을 때만 H.265를 씁니다. 소프트웨어 인코더는 오히려 느리기 때문입니다.
  - 끊김: 최대 1600px, 8Mbps, 50ms 버퍼
  - 별도 화면: `--new-display` + `--start-app`
- **이유:** 이 폰(갤럭시 A16)에는 Exynos 하드웨어 H.265 인코더가 있습니다(실제 확인).

## D-006. cmd 창이 싫다 → 데스크톱 앱으로 (2026-11-25)
- **고민:** 검은 cmd 창에서 쓰는 게 마음에 들지 않습니다. 앱처럼 쓰고, 기능도 마음대로 추가하고 싶습니다.
- **선택지:** Kotlin Compose Desktop / Python / C# WPF / 웹(Electron)
- **결정:** **Kotlin Compose Desktop**
- **이유:** IntelliJ와 안드로이드 개발에 익숙해서, 안드로이드와 같은 방식으로 고칠 수 있습니다.
- **구조 결정:** 옵션과 빠른 기능은 `features/` 폴더의 목록에 한 줄만 추가하면 화면에 자동으로 나타나게 했습니다.

## D-007. 무선 디버깅은 항상 켜져 있어야 하나? (2026-11-25)
- **답:** scrcpy 방식에서는 미러링하는 동안만 켜져 있으면 됩니다. 알림창 빠른 설정에 "무선 디버깅" 타일을 추가하면 켜고 끄기가 편합니다.

## D-008. ⭐ 보안 위험 자동 차단을 꺼야만 무선 디버깅이 된다 (2026-11-25)
- **고민:** 삼성 "보안 위험 자동 차단"은 adb(무선 디버깅)를 막습니다. scrcpy를 쓰려면 매번 보안 기능을 꺼야 합니다.
- **선택지:**
  1. 쓸 때만 끄고 다 쓰면 다시 켜기 (번거로움)
  2. Windows "휴대폰과 연결" (자동 차단을 켠 채 가능, 하지만 기능 추가 불가)
  3. **폰에 직접 만든 앱 설치** (adb 없이 일반 앱 권한으로 화면 보내기와 조작 받기)
- **결정:** **3번**
- **이유:** 자동 차단을 켜둔 채로 쓸 수 있고, 폰 쪽 기능까지 마음대로 추가할 수 있습니다.
- **남은 걱정:** 직접 만든 앱이 자동 차단을 켠 상태에서도 동작하는지 → 0단계 테스트로 확인하기로 했습니다(D-011).

## D-009. 3번 방식은 결국 "scrcpy를 직접 만드는 것"인가? (2026-11-25)
- **정리:** 맞습니다. 다만 결정적인 차이가 있습니다.
  - scrcpy의 폰 쪽은 앱이 아닙니다. adb로 밀어 넣어 **shell 권한**으로 실행해서, 허락 없이 캡처하고 터치를 시스템에 직접 넣습니다.
  - 우리 앱은 **일반 앱 권한**만 가집니다. 화면은 MediaProjection으로 캡처하고 매번 허락을 받습니다. 터치는 접근성 서비스로 흉내 냅니다.
- **결정:** 매번 폰에서 허락하는 방식은 **오히려 좋다**고 판단했습니다. 모르는 사이에 화면이 넘어갈 일이 없습니다.

## D-010. 접근성 "제스처 흉내"는 scrcpy와 기능이 같나? (2026-11-25)
- **같은 것:** 탭, 길게 누르기, 스와이프, 두 손가락 확대, 뒤로가기·홈·최근 앱·알림창, 일반 앱 글자 입력(한글은 오히려 쉬움)
- **약한 것:**
  - 실시간 드래그(그림, 게임)가 덜 부드럽습니다.
  - 휠 스크롤이 덜 정확합니다(관성).
  - 방향키, Tab, 단축키 같은 특수 키를 보낼 수 없습니다.
  - 일부 앱(게임, Flutter, Unity)은 글자 입력란을 찾지 못합니다.
  - 국내 은행 앱이 접근성 앱을 막을 수 있습니다.
- **추가로 알게 된 점:** 글자 입력 문제는 scrcpy도 한글에서는 비슷했습니다. 기본 방식으로는 한글이 안 되고, uhid로 해결했습니다. 우리 앱도 **키보드 앱(IME) 방식**까지 만들면 scrcpy uhid와 비슷한 수준이 됩니다.

## D-011. 0단계: 정말 자동 차단을 켠 채 동작할까? (2026-11-25)
- **방법:** 최소 테스트 앱(PM 테스트 0.1)으로 접근성 제스처, 화면 캡처, 브라우저 조작을 확인합니다.
- **결과:** ✅ 자동 차단을 **다시 켠 상태에서도** 모두 동작했습니다.
- **알게 된 장벽 (설치할 때만):**
  - 자동 차단: 설치하는 동안 잠깐 꺼야 합니다.
  - Play 프로텍트: 파일로 받은 APK가 접근성 권한을 쓰면 "기기 보호를 위해 앱이 차단되었습니다"로 막습니다. **adb로 설치하면 됩니다** (Phone Mirror의 [APK 설치] 버튼).
- **남은 걱정:**
  - 나중에 Play 프로텍트가 이 앱을 다시 검사해서 막는지
  - 한글 입력은 아직 확인하지 않았습니다.

## D-012. 테스트 앱이 느리고 드래그가 너무 많이 된다 (2026-11-25)
- **원인:**
  - 느림: 사진을 한 장씩 요청합니다(왕복이 쌓임). JPEG를 CPU로 만들고, 드래그는 놓은 뒤에야 실행됩니다.
  - 드래그 과다: 짧은 시간에 그은 스와이프를 안드로이드가 "빠르게 튕김"으로 보고 관성을 줍니다.
- **선택지:**
  - A. 테스트 앱을 먼저 빠르게 고쳐서 확인
  - B. 바로 정식 "앱 모드"를 만들면서 한꺼번에 해결
- **결정:** **A**
- **이유:** 영상 속도(H.264)는 scrcpy가 이미 증명한 방식이라 확실합니다. 반면 실시간 드래그와 관성 제거는 직접 해봐야 아는 부분이라, 불확실한 것부터 작게 확인하기로 했습니다.

## D-013. 실시간 드래그를 어떻게 이어 붙일까? (2026-11-25)
- **고민:** 코드 검토에서 "구간을 하나씩 보내고 끝나면 다음을 보내는" 구조는 구간마다 추가 시간이 쌓여 지연이 0.15~0.3초까지 늘어난다는 지적이 나왔습니다.
- **선택지:**
  1. 구간을 2개씩 동시에 보내기: 더 부드러울 수 있지만 안드로이드 문서에 없는 동작에 기대야 합니다.
  2. 한 번에 하나씩 보내되, 구간을 50ms 이하로 자르고 추가 시간만큼 재생을 당기기
- **결정:** **2번** (0.3에 반영)
- **이유:** 문서에 있는 동작만 써서 기종이 달라도 안전합니다. 실제로 써보고 부족하면 1번을 시험합니다.

## D-014. 노트북 앱은 재사용하지 않고 새로 만든다 (2026-11-25)
- **고민:** 0.3에서도 속도가 아쉬웠습니다(errors E-011). 해결하려면 H.264가 필요하고, 브라우저는 보안 규칙 때문에 `http://` 주소에서 H.264를 직접 해독할 수 없습니다. 그래서 노트북 앱이 필요합니다. 그런데 지금 Phone Mirror는 연결 기능(찾기, 페어링, 미러링, 빠른 기능)이 전부 scrcpy와 adb(무선 디버깅)에 묶여 있어서, 자동 차단을 켜면 하나도 동작하지 않습니다.
- **선택지:**
  1. Phone Mirror 하나에 "scrcpy 모드 / 앱 모드"를 같이 넣기 (틀 재사용, 코드 두 갈래)
  2. **앱 모드 전용 노트북 앱을 새로 만들기** (scrcpy와 adb에 묶이지 않음)
- **결정:** **2번.** 재사용하지 않고 새로 만듭니다.
- **이유:** 앞으로의 방향은 자동 차단을 켠 채로 쓰는 것입니다. scrcpy와 adb에 묶이지 않은 깨끗한 구조가 더 단순하고 고치기 쉽습니다.
- **남은 걱정:** 기존 Phone Mirror를 어떻게 정리할지, 새 앱의 이름과 첫 버전 범위

## D-015. 새 앱 Linky의 구조와 첫 버전 범위 (2026-11-25)
- **정한 것 (사용자 선택):**
  - 이름: **Linky** (노트북 앱과 폰 앱 모두)
  - 기존 scrcpy용 Phone Mirror, 초기 스크립트, scrcpy 파일: **휴지통으로 삭제**
  - 첫 버전 범위: **보기 + 조작 + H.264 + 보안(페어링·암호화)** 한 번에
- **구조 결정:**
  - `desktop/`(노트북 앱), `android/`(폰 앱), `shared/`(통신 규칙)로 나눈다. 두 앱은 Kotlin 버전이 달라(데스크톱 2.4.21, 안드로이드 AGP 내장 2.2.x) 한 빌드에 넣으면 충돌한다. 그래서 빌드는 따로 하고, `shared` 소스 폴더만 양쪽이 같이 컴파일한다.
  - 0단계 앱(`android-probe/`)은 검증된 코드(실시간 드래그 엔진, 접근성 서비스, 캡처 규칙)의 출처라서 남겨둔다.
- **보안 방식:**
  - 각 기기가 자체 서명 인증서(EC P-256)를 만들고 **상호 TLS**로 암호화한다.
  - 처음 연결할 때는 **블루투스식 숫자 비교 페어링**을 한다. 양쪽 화면에 같은 6자리가 보이면 확인하는 방식이다.
  - 그 뒤로는 서로의 인증서 지문을 기억해서 그 기기만 받는다.
  - 약속값(commit) 단계를 넣어, 중간에 끼어든 사람이 숫자를 맞추려고 여러 번 시도할 수 없게 했다.
  - 이유: 직접 만든 암호화 대신 표준 TLS를 쓰고, 처음 한 번만 사람이 확인하면 된다.
- **영상 방식:**
  - 폰은 MediaCodec 하드웨어 H.264로 인코딩한다. 저지연 설정, B-프레임 없음, 화면이 멈춰도 100ms마다 반복한다.
  - 노트북은 FFmpeg(avcodec)를 직접 호출해 해독한다. JavaCV의 간편 기능은 버퍼링 지연이 있어 쓰지 않는다.
  - 보는 노트북이 없을 때는 인코딩하지 않는다.
- **폰 찾기:**
  - 폰 앱이 직접 mDNS로 알리고(`_linky._tcp`), 노트북은 Wi-Fi 등 각 네트워크마다 JmDNS로 찾는다.
  - 노트북에 VPN 어댑터가 여러 개 있어서(Radmin, WARP 등), 기본 설정으로는 Wi-Fi를 못 잡을 수 있기 때문이다.
- **설계서:** [linky-design.md](linky-design.md)

## D-016. 검토 결과 반영 방침 (2026-11-26)
- **고민:** Linky 첫 구현을 4개 관점으로 검토하니 39건이 나왔습니다(errors E-012). 무엇을 고치고 무엇을 둘지 정해야 했습니다.
- **결정:**
  - 38건은 고치고, 1건(폰이 모든 네트워크에서 연결을 받는 점)은 그대로 둡니다. Wi-Fi 주소에만 묶으면 폰 핫스팟으로 쓰는 경우가 막히고, TLS와 페어링이 이미 보호하기 때문입니다.
  - 가장 중요한 것은 **페어링 창 하나에 시도 한 번**입니다. 공격자가 숫자를 보고 끊는 시도를 반복하지 못하게 합니다.
  - **자동 연결은 페어링하지 않습니다.**
  - **"닮은 기기" 판단을 두 단계로 나눴습니다** (2차 검증 반영):
    - mDNS 지문 앞부분이 같은데 인증서가 다르면 → 강하게 거부합니다(위장 가능성 높음).
    - 이름이나 주소만 같으면 → 막지 않고, 직접 페어링할 때 경고만 보여줍니다. 처음에는 이것도 막았는데, 그러면 이름이 같은 두 번째 폰(예: 갤럭시 A16 두 대)은 아예 페어링할 수 없었습니다.
- **남은 걱정:** 실제 폰에서는 아직 한 번도 실행하지 않았습니다. 다음 확인 항목이 남아 있습니다.
  - 안드로이드에서 인증서 파일 저장·읽기
  - TLS 서버 동작
  - 인코더 크기와 지연 건너뛰기
  - 알림 버튼
